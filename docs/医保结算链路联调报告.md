## 一、这条链路跑了什么

不是伪造报文，是 HIS 自己的接口发起的真实报盘：

```
HIS(8080 /api)  --[2304 报盘]-->  前置机 csmig(8091 /mig)  --[转发]-->  医保局端 csmis(8096 /mss)
      ▲                                    │                              │
      │                                    │                              │

            院内段：预共享 SM4 + SM2 签名        局端段：SM2 数字信封
```

调用入口：`POST /api/charge/settlement/upload?id=2103793967031144450`
业务对象：结算清单 `IS2026092600017`（患者张伟，账单 `SB2026092600079`，总费用 200，医保支付 170，自付 30）

CA 不在这条报文流里，这符合真实规范：CA 只签发证书，运行时每次加解密/签名都是两端各用本地私钥+对端公钥直接算，CA 不上线。

### 4. 为什么能确认「局端真的用私钥解了 keyEnc」

`encData` 是用**每次转发随机生成的 16 字节 SM4 会话密钥**加密的，前置机自己不保存这把密钥，只把它用局端公钥 SM2 加密后放进 `keyEnc`。因此局端要能解出 `msgType: 2304` 这样的明文并返回成功回执，**只有一种可能：它用 csmis 自己的 SM2 私钥解开了 `keyEnc`，拿到会话密钥，再用会话密钥解 `encData`**。预共享的 `sm4-key-mss` 在这条路径上根本不参与。

## 四、切换成你自己那套的顺序（顺序反了必失败）

局端先起、前置后起。前置机启动时会加载局端公钥并打印「局端段安全通道就绪（前置↔医保局，SM2 数字信封）」；如果先起前置、局端还没准备好，第一次转发会报验签解密失败。

1. 停 `8090`，用新 `mis-backend.jar` 重启（`crypto/csmig-public.pem` 必须在包内）
2. 停 `8091`，用新 `mig-backend.jar` 重启，`mig.upstream.base-url` 指回 `http://localhost:8090/mss`
3. `csmig/crypto/` 下要有 `csmis-public.pem`，`csmis/crypto/` 下要有 `csmig-public.pem`（只交换公钥，私钥不出本机）
4. HIS 不用动

当前状态：`8091`（我起的新前置机）+ `8096`（我起的新局端）仍在运行，`8090`、`8092`、`8080` 是你的原进程。

| 项 | 现状 | 真实要求 |
|---|---|---|
| 报文层加密 | SM4 数字信封 + SM2 签名（**已符合方向**） | GB/T 45938—2025 9.3「采用国密算法进行数字信封加密」 |
| 证书来源 | 三端证书均由自建 csssl 签发（仿真） | 国家医保信息平台统一 PKI/CA 体系生成、安全通道下发、一机一证书 |
| 私钥存放 | 明文 PEM 在 `resources/crypto/` | 密钥须在密码模块内（GM/T 0028 二级以上、商用密码产品认证） |
| 局端 | `csmis` 自建模拟 | 真实局端是省医保平台，报文逐字段要按省规范核 |
| 网络层 | 局域网 HTTP | 医保专线 + 国密 VPN（IPsec）/ 机构侧国密安全网关 |

## 七、撤销后重报的 500 缺陷（已修）

**现象**：四服务按新代码重启后实跑 2304，返回 `code=500 医保结算异常：医保平台处理失败：500`，错误文案里嵌着一段带 `keyEnc` 的回执信封。

**逐层排除**（别一看到 500 就怀疑加密，加密这层反而是好的）：

- `EnvelopeProbe` 以前置机身份直连 8090 → HTTP 200，回执明文是 `2304 报文缺少结算清单号 settlementNo`（8090 正常解开了数字信封，只是嫌探针没带业务字段）
- `FullChainProbe` 经 8091 → 8090 → 同样 200，说明 HIS→前置→局端整条链通
- 把 HIS 台账里那条真实报文（`biz_yb_report.payload` 1394 字节）原样复放给 8090：**用旧 `tradeNo` → 200 成功（命中幂等，回原回执）；换成新 `tradeNo` → HTTP 500「系统内部错误」**

**根因**：`mis_settlement` 上有唯一键 `uk_sett_settlementno(settlement_no)`，而 `receive2304` 的幂等只判 `trade_no`。HIS 撤销（2305）后重新报盘会换新 `tradeNo`、但 `settlementNo` 不变，`insert` 直接撞唯一键，异常冒到全局处理器变成 500。真实业务里"撤销报盘 → 修正后重报"是标准流程，这一步必须受理，属于业务缺陷而不是加密问题。

**修复**（`SettlementGatewayServiceImpl.receive2304`）：

- 新增 `bySettlementNo` 判断，放在 tradeNo 幂等之后：
  - 原单 `status=2`（已撤销）→ 在原单上恢复受理：换新 `tradeNo`、重出回执号（加 `R` 后缀）、`cancel_time` 置 NULL
  - 原单 `status=1`（在保）→ 明确业务拒绝 `infcode=-1`「结算清单号 xxx 已存在有效结算单，请先撤销该笔再重新报盘」，不再 500
- 踩到一个 MyBatis-Plus 坑：`update(entity, wrapper)` 里 entity 若还带着旧 `cancelTime`，会把 wrapper 的 `set(cancelTime, null)` 覆盖回去，库里撤销时间清不掉。必须先 `s.setCancelTime(null)`（让 MP 忽略该字段）再交给 wrapper 显式写 NULL。

**实测（8093 临时实例跑新代码）**：

| 场景 | 结果 |
|---|---|
| 已撤销单同号重报 | HTTP 200、`infcode=0`、回执号 `…1400R`、note「撤销后重新报盘，已在原结算单上恢复受理」；库内 `status` 2→1、`cancel_time` NULL、`trade_no` 换成新流水 |
| 在保单换新流水再报 | HTTP 200、`infcode=-1`、文案「已存在有效结算单（流水 xxx），请先撤销该笔再重新报盘」 |

测试用的 `PROBE-*` 数据已全部删除；你那笔 `IS2026092600017` 未受影响（仍为 `status=2 / cancel_time=13:16:48`）。

**生效条件**：8090 目前跑的还是旧代码，重启一次才会加载这次修复。
