# 后端模块化拆分实施方案（图纸版 / 不改代码）

> 状态：**已实施（2026-11-23）**。设计口径见正文，实际落地与偏差记录见第九节。
> 适用工程：`source/ssl_backend`（父工程 `csssl-parent`，当前仅 1 个子模块 `csssl-web`）。

---

## 一、结论先行

1. **现状确实不是多模块**：`ssl_backend/pom.xml` 是 `packaging=pom`，`<modules>` 里只有 `csssl-web` 一个。父工程不统管任何依赖版本（`spring-boot-starter-parent` 是子模块自己挂的），属于"一个单体工程 + 一个空壳父目录"。
2. **"那个乱七八糟的模块"是 `csssl-sdk`**：`dc5b175` 拆出来过（csssl-sdk + csssl-web 双模块），`c92df13` 又"整合 SDK 模块"合回了 server。父 pom 注释里仍留着 `csssl-push-sdk` 字样，是没清掉的历史残留。
3. **目标不是拆成微服务**：构建期拆 5 个 module，运行期仍是一个可执行 jar、一个进程、一套 compose。Docker / K8s / 前端代理全部不动。
4. **`store-dir` 改造前置做**：拆模块最大的坑是"启动目录一变就多落一套 `data/certs`、换一把 KEK，库内密文全解不开"（`2026-11-15` 事故）。本方案把它改成**显式绝对路径**，彻底废掉"向上找含 `<modules>` 的 pom"的猜测逻辑。这一步先做，后面拆模块就再没有这个雷。

## 四、父工程要先扶正

现在父 pom 只是 `<modules>` 列表 + BouncyCastle 两条 `dependencyManagement`，子模块各自挂 `spring-boot-starter-parent` 并重复声明 5 个 version 属性。拆之前必须改成标准结构：

```xml
<!-- ssl_backend/pom.xml -->
<parent>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-parent</artifactId>
  <version>3.2.5</version>
  <relativePath/>
</parent>
<packaging>pom</packaging>
<modules>
  <module>csssl-common</module>
  <module>csssl-workflow</module>
  <module>csssl-ca</module>
  <module>csssl-sdk</module>
  <module>csssl-web</module>
</modules>
<properties>java 21 / mybatis-plus / hutool / jjwt / bc …</properties>
<dependencyManagement>…统管全部版本…</dependencyManagement>
```

子模块统一 `<parent>` 指向 `csssl-parent`，只声明自己用到的依赖且不写版本。**只有 `csssl-web` 挂 `spring-boot-maven-plugin` 的 `repackage`**，其余模块 `packaging=jar`、不打可执行包。`finalName` 保持 `csssl-backend`，产物名不变。

## 五、`store-dir` 改为显式绝对路径（前置项 P0）

### 5.1 目标值

```
E:/work_source/his_cslk/csssl/source/ssl_backend/data/certs
```

即 `ssl_backend/data/certs`，也就是当前 `master.key` 实际所在目录（已确认存在 `data/certs/master.key` 与 `data/certs/companies/91430100MA4L5K2N3T/`）。

### 5.2 决策

- **废除** `KeyVaultConfig#backendRoot()`：不再从 classpath 逐级向上找"含 `<modules>` 的 pom"。
- 配置里**不再给相对路径默认值**；相对路径视为配置错误，启动即失败（fail-fast），宁可不启动也不要静默落第二套盘。
- 环境差异一律走 `SSL_STORE_DIR`：
  - 本机 dev → 写死 `E:/…/ssl_backend/data/certs`
  - 容器 → `/app/data/certs`（compose 挂载 `./data:/app/data`）

### 5.3 三处配置改动

`application.yml`（入库，去掉相对兜底）：

```yaml
csssl:
  # 必须是绝对路径：dev 见 application-dev.yml，容器见 compose 的 SSL_STORE_DIR
  store-dir: ${SSL_STORE_DIR}
```

`application-dev.yml`（不入库，写死本机绝对路径，正斜杠）：

```yaml
csssl:
  store-dir: ${SSL_STORE_DIR:E:/work_source/his_cslk/csssl/source/ssl_backend/data/certs}
```

> 注意：YAML 里不要用未加引号的反斜杠 `E:\work_source\…`（`\w` 会被当转义）。用正斜杠，或整体加单引号。

`docker/docker-compose.yml`（新增环境变量，不依赖任何猜测逻辑）：

```yaml
    environment:
      TZ: Asia/Shanghai
      SSL_STORE_DIR: /app/data/certs
      JAVA_OPTS: -Xms384m -Xmx1g -XX:+UseG1GC -Duser.timezone=Asia/Shanghai
```

### 5.4 代码改动（伪码，示意，不落工程）

```java
static Path resolveStoreDir(String configured) {
    if (configured == null || configured.isBlank()) {
        throw new IllegalStateException(
            "csssl.store-dir 未配置：必须显式指定绝对路径（dev 见 application-dev.yml，容器见 SSL_STORE_DIR）");
    }
    Path p = Path.of(configured);
    if (!p.isAbsolute()) {
        throw new IllegalStateException("csssl.store-dir 必须是绝对路径，当前为: " + configured);
    }
    return p.normalize().toAbsolutePath();
}
// 删除 backendRoot() 方法与其 import（IOException / URISyntaxException）
```

### 5.5 迁移纪律与验收

- **只改"怎么算路径"，绝不移动/复制/删除 `data/certs` 里的任何文件**。`master.key` 一旦换位置或换内容，`ssl_key_vault` 全部密文永久解不开。
- 改前先记下启动日志里的旧指纹：`[密钥保险库] default 域 store-dir=… KEK 指纹=…`。
- 改后必须用同一套库重启一次，日志打印的 `store-dir` 等于目标值、`KEK 指纹`与改造前**完全一致**，登录、证书列表、签发、CRL 全链路正常。
- 容器侧同样核对指纹（compose 的 `./data` 与宿主 `ssl_backend/data` 是否同一个物理目录，需先确认实际部署关系，避免出现两把 KEK）。

## 七、风险与红线

1. **KEK / store-dir（最高优先）**：位置一动就换 KEK。P0 完成后这条风险归零；后续所有步骤不得再碰 `data/certs` 与 `SSL_STORE_DIR` 的取值。
2. **Mapper 扫描**：`CssslApplication` 现在是 `@MapperScan("com.csssl.mapper")` 单包。拆后必须显式列全（`{"com.csssl.mapper","com.csssl.workflow.mapper"}`）或统一改用"各模块固定 `xxx.mapper` + 一次列全"。漏写症状是启动报 `No qualifying bean of type XxxMapper`。
3. **mapper XML 路径**：`mybatis-plus.mapper-locations: classpath*:mapper/**/*.xml` 已用 `classpath*`，可跨 jar 扫描，不要在拆分时改成 `classpath:`。XML 若搬进模块，要确认随 `resources` 打进 jar。
4. **可执行包唯一**：`spring-boot-maven-plugin` 只允许出现在 `csssl-web`。其他模块出现 `repackage` 会产生不可被依赖的 fat jar，`mvn install` 时互相污染。
5. **不许拆成独立进程**：模块化只解决编译期边界。不做 RPC / 消息总线 / 独立部署，compose、nginx、端口、context-path `/ssl` 全部不动。
6. **启动目录不再敏感，但仍统一**：P0 后路径与 cwd 无关，这是核心收益；同时构建/启动命令继续在 `source/ssl_backend` 下执行（`mvn -q -DskipTests compile`、`mvn -spring-boot:run -Dspring-boot.run.arguments=--server.port=8093`），减少团队心智负担。
7. **`ResolveStoreDir` 的 fail-fast 会打破现有容器**：compose 未设 `SSL_STORE_DIR` 时容器将直接启动失败。P0 必须与 compose 改动同一次提交，不能只改一半。
8. **`WorkflowTodoService` 的位置**：它 import 了 9 个证书域 entity，P3 时**不要**顺手搬进 workflow，否则 workflow 反向依赖 ca，形成环。

### 9.4 与设计的偏差（有意为之）

| 项 | 设计 | 实际 | 原因 |
|---|---|---|---|
| `UsccValidator` | common | **ca**（`com.csssl.util` 包不变） | 它 import 了 `CaCompany`，留在 common 会让 common 反向依赖 ca |
| `CrlViewVO` | common | **ca** | 复用了 `CertVO`，而 `CertVO` 依赖 `CaCert` |
| `CaSystemVO` | common | **ca** | 直接引用 `CaSystem` 实体 |
| `csssl-sdk` 内容 | "DTP + 验签" | 4 个纯密码工具类 | DTP 报文目前仍由 `HisPushService` 内联构造，未抽独立报文对象；先保证 sdk 零 Spring 依赖、可被外部直接引用 |
| `csssl-common` → sdk | 依赖 common 子集 | **不依赖** | 实际 common 没有用到 sdk 的 4 个类；保持两侧都是底座更干净 |

### 9.5 第二轮：common 去业务化（新增 `csssl-system`）

第一轮把用户/角色/权限、审计、密钥保险库连同 DTO/VO 一起塞进了 common，common 因此背了 8 个 entity、6 个 mapper、5 个 service、55 个 DTO、35 个 VO。第二轮按「common 只放基础设施，业务模型归各自域」重排：

- **新增 `csssl-system`（用户与权限域）**，插在 common 与 workflow 之间。之所以必须低于 workflow：`WorkflowEngineService`/`WorkflowRegistry` 依赖 `LoginUser`、`SysUser`、`SysUserMapper`、`UserUtils`、`UserSimpleVO`，只有 system 在下面才不成环。
- common 迁出：`AuditColumns`、`LoginUser`、`SysUser`、`SysRole`、`RolePerm`、`KeyVaultEntry`、`Message`、`AuditLog` + 6 个 mapper + `AuthService`/`PermissionService`/`MessageService`/`AuditService`/`AuditSigner` + `UserUtils`/`KeyVault` + `KeyVaultConfig`/`AuditMetaObjectHandler`。
- DTO/VO 按归属重分：登录/用户/角色/权限/审计/消息 → system；工作流 4 个 DTO → workflow；证书域 39 个 DTO + 27 个 VO → ca。**common 的 dto/vo/entity/mapper/service 五个目录已删除。**
- 一个刻意例外：`ChainVerifyVO`/`ChainBrokenVO` 归 system 而不是 ca——它们只被 `AuditService`（审计链完整性校验）和 `AuditController` 使用，属于审计域。
- `csssl-common` 从 135 个类缩到 24 个，只剩 `common`、`config`（`CssslProperties` + Jackson/MyBatis/Scheduling/Web）、`enums`、`util`。

第二轮验证：`mvn clean compile` 逐模块 4 / 24 / 48 / 35 / 115 / 27 全部通过；打包内嵌 5 个内部模块 jar（`csssl-sdk`、`csssl-common`、`csssl-system`、`csssl-workflow`、`csssl-ca`）；8095 启动成功，`store-dir` 与 KEK 指纹仍为 `1f8b938aa586`（未变），`/ssl/auth/publicKey` 200、无令牌 `/ssl/admin/certs/page` 401。

### 9.6 第三轮：server 只留启动类与 config

server 原本还剩 19 个 controller、3 个 api controller 和 `WorkflowTodoService`，不符合「server 只做装配」。第三轮按「controller 跟随它依赖的域」全部下放：

| 去向 | 内容 | 理由 |
|---|---|---|
| `csssl-system` | `AuthController`、`AdminUserController`、`RoleController`、`AuditController`、`MessageController`（5 个） | 只依赖登录态、用户角色、审计、消息服务 |
| `csssl-workflow` | `WorkflowDefController`、`WorkflowEngineController`（2 个） | 只依赖流程定义/引擎，不碰证书域 |
| `csssl-ca` | 12 个证书域后台 controller + `api/controller` 3 个 + `WorkflowTodoService` + `WorkflowController` | 都直接读写证书域实体/服务 |
| `csssl-web` | 只剩 `CssslApplication` + `SecurityConfig` + `TokenAuthFilter`（3 个类） | 纯装配与安全 |

三个必须解释的例外：

- **`WorkflowTodoService` 与 `WorkflowController` 一起落在 ca**：前者 import 9 个证书域实体，放进 workflow 立刻成环；后者注入前者，只能跟着上来。
- **`CaApiAuthFilter` 从 server 挪到 ca**：`CaApiController` 要用它的 `@RequestAttribute` 常量（`ATTR_CLIENT`/`ATTR_BODY_SHA256`），留在 server 会让 ca 反向依赖 server。过滤器本身只依赖 `ApiClientService`（ca）与 sdk 的验签工具，落在 ca 自洽；`SecurityConfig` 仍在 server 里挂载它，方向正确。
- **通用入参 DTO 按「最低使用方」归位**：`IdDTO` → workflow（ca 的 controller 复用），`CodeDTO`/`CompanyUsccDTO`/`ChainVerifyQueryDTO` → system（角色、用户、审计复用）。同时清掉了 `AdminUserController` 里一个从未被调用的 `CompanyService` 注入（否则 system 会反向依赖 ca）。

第三轮验证：`mvn clean compile` 逐模块 **4 / 24 / 56 / 38 / 128 / 3**；`csssl-web/target/classes/com/csssl` 下确实只有 `CssslApplication.class`、`config/SecurityConfig.class`、`config/TokenAuthFilter.class` 三个类。8096 启动 7.97 秒，KEK 指纹仍 `1f8b938aa586`；`/ssl/auth/publicKey` 200（controller 在 system 仍被扫到）、无令牌 `/ssl/admin/certs/page` 401、`/ssl/ca/api/v1/*` 无签名 401（说明挪到 ca 的过滤器仍挂在链上）。
